# 全局急停只存进程内存，语义是停止接收而非停止执行

管理后台提供一个全局急停开关，按下后系统对所有新的入站 QQ 消息一律回复维护提示，不建用户、不建会话、不写消息记录、不占用入站去重表。它是失控时的止损手段：上游 DeepSeek 或 arXiv 故障、成本异常上涨、或刚上线的改动明显跑错时，管理员需要一个比 `docker compose stop` 更轻、又能立刻生效的动作。

急停状态只存在进程内存里（一个原子指针，`nil` 即正常接收，非 `nil` 时同时携带触发时间与原因，避免开关和元数据成为两个可能互相矛盾的字段），既不进环境变量也不进数据库。这是 ADR 0008「配置与静态数据不进数据库、阈值和开关从环境变量读取」的一个显式例外，理由是那条约定服务于可审计与可回滚，而急停两者都不需要：它不改变任何行为参数，只是暂时不接活。环境变量做不到运行时生效，而为一个布尔值新建第五张表会破掉四表约束，收益不足。

代价是**容器重启会自动解除急停**，这一点是刻意选择而非疏漏。能跨重启存活的急停是一个静默陷阱：某天没人记得按过它，服务停摆而健康检查全绿、日志无异常，排查会非常昂贵。急停的前提本来就是「有人正在现场盯着」，人在场时重启解除是安全的；人不在场时应该停容器，而不是依赖一个持久化的软开关。

急停**不中断已经在执行的任务**。入站消息由 per-openID 的 worker goroutine 处理，往下传的是 app 级 context；要取消 in-flight 任务需要新增一个 per-task context 注册表。考虑到在跑的任务最多十几个、几十秒内自然结束，而真要立刻切断执行，停进程比一个半成品的取消机制更彻底也更诚实，所以这里划清界限：急停管入口，不管已经进门的。这条界限必须体现在术语上——「全局急停」在 CONTEXT.md 里定义为停止接收，「任务取消」是另一个词。

停机期间的入站消息一律丢弃，不入库排队等恢复后补跑。排队补跑看起来更友好，但会在解除急停的瞬间对 DeepSeek 打出一个流量尖峰，而急停的起因往往正是上游故障或成本失控，那个尖峰会把刚止住的问题立刻再放一遍。丢弃并明确告知用户，把重试的决定权交回给人。

已排除的相邻选项：成本熔断（按日成本阈值自动进入急停）当前不做，因为可信的成本拆分统计刚刚才上线，阈值必须来自观测到的真实曲线而不是预先拍的数字；任务取消同样不做。三者在 CONTEXT.md 里是三个独立词条，不合并成一个开关——它们的触发者、作用粒度和可逆性都不同，合并会做成一个谁都不敢按的按钮。
