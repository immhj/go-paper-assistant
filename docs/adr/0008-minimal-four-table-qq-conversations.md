# QQ 命令式多会话使用四张最小业务表

第一版不提供用户 Web 端，只提供 QQ Bot 单聊与管理后台。数据库有 `users`、`conversations`、`papers`、`messages` 四张业务表，共 37 个字段（`users` 5、`conversations` 8、`messages` 12、`papers` 12）。

QQ 客户端只有一条物理消息流，不能创建多个聊天窗口；这不等于系统不能有多个会话。系统在数据库中创建应用层独立会话。会话命令收缩到五个：`/new <标题>` 创建并切换、`/list` 查看、`/use <编号>` 切换、`/current` 查看当前会话、`/help` 查看能力；重命名与归档不再有专用命令，改由用户自然语言表达、执行 Agent 调用对应工具落库（见 ADR 0010）。每个会话有独立的 `current_context`、消息窗口和论文序号映射，因此长时间使用不会把所有话题混进同一个模型上下文。

`users.active_conversation_id` 只保存下一条普通 QQ 消息应进入哪个会话。`conversations.current_context` 保存研究方向、结构化检索规格、规格版本、下一个论文序号和“论文 ID → 序号”映射。`conversation_no` 是面向单个用户的稳定编号，`/use 2` 按 `(user_id, conversation_no)` 查询，不能把全局自增主键直接暴露给用户。

`messages` 必须属于一个 `conversation_id`。用户原话滑动窗口只查询当前会话最近约 10 条 `role='user'` 的消息；机器人历史输出默认不进入窗口。`shown_papers` 同时承担候选列表与展示记录，因为机器人发出的那条列表消息本身就是候选列表。序号只在当前会话中唯一，不同会话可以各自拥有 `#3`。

`papers` 跨用户、跨会话共享。论文检索由 `jannisborn/paperscraper` Python sidecar 提供，第一版启用 arXiv API；论文身份使用 `(source, external_id)`。全文正文放 `data/fulltext/`，表中只保存路径和校验状态；非 `ok` 一律不送模型。

任务第一版仍存在进程内存，不建 `tasks` 表。代价是进程重启会丢失执行中的任务，后台任务页只能展示当前进程中的队列与失败记录；当前是单实例、十几名用户的内部工具，这个代价可接受。确实需要重启恢复时再增加任务表。

配置与静态数据不进数据库：CCF 列表计划使用 `config/ccf-2026.json`，提示词后续迁移到 `config/prompts/*.md`，阈值和开关当前从环境变量读取。唯一的例外是全局急停——它必须运行时可改，因此既不在环境变量里也不在数据库里，只存在进程内存中（见 ADR 0011）。管理后台使用环境变量注入账号和密码；非 development 环境会拒绝 `admin/admin` 默认值，并且 Docker 默认只绑定 `127.0.0.1`。提示词最终走文件是因为它能进入 Git 历史，热更新只需重读文件。

表变少不等于复杂度消失，部分结构移到了 JSON 与 Go 代码。在当前规模下这个交换划算；如果后续需要用户 Web 端、跨设备账号绑定、订阅任务重启恢复，再增量加字段或表，不提前为它们建模。
