# 只做一对一单聊，并以流式消息作为主输出通道

本项目只在 QQ 单聊场景运行，不做群聊，也不提供用户 Web 端。群聊的被动回复有效期只有 5 分钟、不支持流式消息、输出对全群可见且会刷屏，而单聊有 60 分钟有效期、支持流式、天然私密。检索与精读都是耗时的长任务，单聊是唯一能承载它们的场景。

QQ 客户端只有一条物理消息流，不能创建多个聊天窗口；系统在数据库里提供应用层多会话来补足这一点。用户通过 `/new` 创建、`/list` 查看、`/use` 切换，每个会话拥有独立的模型窗口、检索规格和论文序号。切换后所有回复首行都应显示 `[会话 #N · 标题]`，避免用户在同一个 QQ 窗口里忘记当前上下文。

被动回复的真正约束不是时长而是次数：**对一条用户消息最多回复 4 次**，且有效期绑定在单条消息上——用户每发一条新消息就重新获得 60 分钟和 4 次。因此对话可以持续数天，"窗口关闭导致对话中断"不会发生；会有问题的是一次响应想输出多段内容（检索规格确认、命中数量、逐篇速览）时把 4 次配额用光。

解法是把一次完整响应做成**一个流式消息**：流的所有分片共用同一个 `stream_msg_id` 和同一个 `msg_seq`，因此一整个流只消耗 1 次配额，同时用户从第一秒就能看到进度在增长。剩余 3 次配额留给澄清追问、术语扩充建议和错误告知。

两个必须在推送层实现的配套逻辑：流式响应返回的 `remain_msg_len` 需要逐片检查，接近耗尽时提前结束并标记截断；任务执行超过被动回复窗口则返回失败日志，用户需要重新发起。第一版任务只存在进程内存，不承诺跨重启恢复或延期交付；需要这项保证时必须先增加持久化任务/发件箱，而不是把结果塞进普通消息记录。

> 待验证：官方文档没有明文说明"一个流只算 1 次被动回复"，此结论由官方示例（所有分片 `msg_seq` 均为 1）与去重规则（`msg_id + msg_seq` 判重）推导得出。这是整个输出方案的基础，应在开发第一步实测确认。
