# 从单通道 QQ 机器人转向研究生工具集 Web 平台

项目起点是一个只在 QQ 单聊里用的论文助手，`CONTEXT.md` 与 `schema.sql` 都白纸黑字写着「不提供用户 Web 端」。现在方向变了：它要成长为一个面向研究生的**工具集平台**，论文助手只是接入的第一个工具，后续还会有别的工具。这条 ADR 记录这次方向转变本身，它显式推翻上述「不提供 Web 端」的前提；具体的通道、身份、准入分别由 ADR 0013、0014、0015 承接。

转变的实质不是「给论文助手加个网页」，而是在论文助手之上多出一层平台：平台负责账号、登录、准入和工具导航，对每个工具只做「注册 + 鉴权 + 导航」，不侵入其内部领域。这条边界很重要——它决定了接入第二个工具时不需要重构平台，只是多注册一个工具。因此仓库从此有两个限界上下文（见 `CONTEXT-MAP.md`），词汇不再共享，尤其「用户」（QQ 匿名标识）与「账号」（平台登录身份）必须分开。

**代码形态选单体单服务**，不拆微服务。现在就是一个单二进制、一个 MySQL、`go.mod` 只有两个直接依赖，这种克制是刻意的。平台层与工具都活在同一个进程里，工具通过一个轻量的「工具注册」概念挂进导航与路由。微服务会引入部署编排、服务间鉴权、跨服务事务这些当前规模根本不需要的成本；等某个工具真的有独立伸缩或独立发布的需求时，再把它拆出去也不迟，那时它已经有清晰的边界可依。

**前端沿用本仓库的零依赖静态风格**，不引入 Vue/node 构建链。管理后台现在就是一个手写的单文件静态页、零构建，这个风格对当前体量足够，也让整个仓库保持「clone 下来就能跑、不需要前端工具链」。界面观感对齐 GopherAI-v2，但用静态 HTML/CSS/JS 还原，而不是照搬它的 Vue 技术栈。若将来某个工具的前端复杂到静态页扛不住，再局部引入框架，不必现在为全局买单。

> 被这条 ADR 推翻的前提要就地更正，否则会留下自相矛盾的文档：ADR 0003 的「不做用户 Web 端」由 ADR 0013 修订，`schema.sql` 里「不做用户 Web 端 / 管理后台不建表」的注释同步更新。ADR 不删除历史，但必须让读者能顺着线索找到现状。

已排除的相邻选项：其一，为平台单开一个新仓库/新服务——被否，因为论文助手的编排、DAO、配置都要被 Web 通道复用，拆库只会制造同步负担；其二，把平台做成一个纯前端 BFF 去调现有后端——被否，账号与准入是有状态的服务端能力，塞进 BFF 只是换个地方建表。
