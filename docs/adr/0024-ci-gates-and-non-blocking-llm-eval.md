# CI 门禁分层：确定性检查挡合并与发布，真实模型评测只出报告

> 状态：accepted

## 背景

CI 原先只覆盖 fmt、vet、race 单测、golangci-lint、sidecar 的 IEEE 单测和镜像构建，全部是确定性检查。真正容易出线上回归的三类问题都在 CI 之外：MySQL 上的事务与约束语义（单测只用内存 fake）、`schema.sql` 与启动时结构校验的一致性、以及规划器与相关性判断的提示词质量。同时 `scripts/release.ps1` 只要求工作区干净，任何本地提交都能直接发布到服务器，不看 CI 结果。

提示词质量只能靠调用真实模型来衡量，而真实调用要花钱、结果不完全稳定、并且需要把模型密钥放进 CI。

## 决策

1. **确定性检查挡发布**：每次 push / PR 运行的检查（单测、MySQL+Redis 集成测试、全新安装结构校验、E2E 冒烟、sidecar 测试、前端内联脚本语法检查、govulncheck、pip-audit）必须全部通过；`release.ps1` 在构建前确认当前提交的 CI 为绿，否则拒绝发布，只有显式 `-SkipCI` 可以绕过。main 不开分支保护，依靠发布门禁兜底。
2. **模型评测分两层**：
   - 回放层随每个 PR 运行：固定的模型原始输出（含格式错误的输出）喂给 Go 侧解码、校验与转移表，验证确定性逻辑，不调用模型。
   - 真实评测层是独立工作流，手动触发或在提示词所在文件变更时触发：用 golden set 调用真实模型，输出规划器与相关性判断的准确率报告和失败用例，**不挡合并、不挡发布**；单次运行有成本硬上限。
3. 覆盖率只展示，不设阈值。

## 后果

线上回归的主要来源有了自动拦截，而提示词改动不会因为模型的偶发波动卡住开发。代价是提示词质量下降不会被自动阻止，需要人看报告；积累稳定基线后可以再决定是否把真实评测升级为门禁，届时应修订本 ADR。

已排除：每个 PR 调用真实模型并以阈值挡合并（花钱、易抖动、密钥暴露面大）；评测只在本地脚本运行（没有历史、容易被跳过）；全局覆盖率阈值（诱导凑数测试）；main 分支保护强制 PR（单人开发收益小于摩擦，真正要挡的是红代码上线）。
