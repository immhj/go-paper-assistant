# 邀请码准入：独立表 + 可设使用次数，管理员生成

> **Superseded：** [ADR 0016](0016-free-guest-access-and-email-verification.md) 已改为免费开放注册、QQ SMTP 邮箱验证、访客资格与成本控制；本文仅保留为历史决策记录，不再作为实现依据。

初期要控制用户增长——既为控成本（每次检索/精读都要花模型钱），也为在小范围内先把体验打磨好。手段选**邀请码准入**：没有有效邀请码就不能注册。这条 ADR 记录邀请码的模型与边界。

**邀请码建独立表 `invite_codes`**，而不是在配置文件里塞一串静态码。理由是邀请码是有状态、会被消费、需要按张追踪的运行时数据：谁生成的、用了几次、还能不能用、什么时候过期——这些都要读写，配置文件表达不了。这也是对 ADR 0008「静态数据不进数据库」的一次合理越界：静态数据指的是阈值、提示词那种只读配置，邀请码是可变业务状态，本就该进库。

**一张码可设使用次数**：`max_uses` 是允许成功注册消费的总次数，`used_count` 是已消费次数。`max_uses = 1` 即一次性码，大于 1 即多人共享码（比如发给一个课题组）。用满即失效。再配一个可空的 `expires_at` 过期时刻，为空表示永不过期。这两个维度（次数 + 时间）覆盖了初期所有发码场景，且都是加列即得、不改结构。

**消费必须原子**：注册时在事务里校验「未过期且 `used_count < max_uses`」并自增 `used_count`，用条件更新（`UPDATE ... SET used_count = used_count + 1 WHERE id = ? AND used_count < max_uses AND (expires_at IS NULL OR expires_at > NOW())`）保证并发下不会把一张一次性码用成两次。账号侧记录 `invited_by_code`，回答「这个人是谁邀来的」。

**邀请码由管理员在管理后台生成**，这也是管理后台从「论文助手后台」升级为「研究生工具管理后台」后，平台级的第一个功能（导航结构见 `docs/contexts/platform/CONTEXT.md`）。生成属于平台域，放在「平台 › 邀请码」一级/二级结构下，与论文助手那几个页面平级而非混在一起。

> 使用次数是「成功注册」的次数，不是「尝试」的次数：校验失败（码错、已满、过期）不消费额度。把两者混同会让一张码被无效尝试悄悄耗尽，是要主动避免的坑。

已排除的相邻选项：其一，配置文件里写死一批静态邀请码——被否，无法按张追踪消费与过期；其二，完全开放注册、事后再封——被否，成本敞口在前，封禁在后，顺序反了；其三，走邮箱验证码而非邀请码（GopherAI 的做法）——被否，验证码防的是机器人注册，防不住「谁能进来」，与「控制增长」是两回事，且引入 SMTP 依赖。
