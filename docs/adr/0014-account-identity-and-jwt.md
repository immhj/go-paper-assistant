# 平台账号身份用独立表 + 可空 QQ 绑定，鉴权用 JWT

> **Partially superseded：** [ADR 0016](0016-free-guest-access-and-email-verification.md) 取代“不验证邮箱”和“JWT 只能等短有效期失效”的结论；独立账号表、身份字段拆分、argon2id、JWT 与管理后台 Basic Auth 分离继续有效。

平台需要一个有凭证的登录身份，而现有的 `users` 表是匿名 QQ 标识（`qq_openid`）、没有任何密码或邮箱。往 `users` 里硬塞登录字段会污染它的语义——它代表「QQ 平台分配的匿名用户」，不是「注册账号」，两者的生命周期、唯一性、可空性都不同。因此**新建独立的 `accounts` 表**，与 `users` 平级共存。

账号身份沿用 GopherAI-v2 验证过的三字段拆分，因为三者的约束和变更频率确实不同：

- **邮箱**是登录凭证，唯一、用户可见、相对稳定；
- **昵称**是展示名，可改、不唯一，绝不能当键；
- **用户名**是系统生成的内部唯一标识，永久稳定、用户不可见，作为账号拥有的一切数据的归属键，写进 JWT。

把归属键（用户名）与登录凭证（邮箱）分开的收益是：用户改邮箱或昵称都不会让历史数据成为孤儿。与 GopherAI 的差异是**不做邮箱验证码**——准入靠邀请码（ADR 0015），邮箱在注册阶段只是一个唯一标识，省掉 SMTP 依赖与 Redis 验证码存储。

**账号与 QQ 用户的关系是可空绑定**：`accounts` 上留一个可空、唯一的 `qq_openid` 列。v1 不强制绑定，绑定后同一个人的 QQ 会话与 Web 会话可以合并查看。选可空列而不是单开一张关联表，是因为一个账号最多绑一个 QQ 身份，一对一关系用列表达最简单；真出现一对多需求时再拆表。

**密码用 argon2id 哈希**，与 schema-full 里给管理员选的算法保持一致，绝不存明文。

**鉴权用 JWT**：面向平台用户，无状态，令牌携带用户名，天然适合「一次登录、多个工具共享登录态」。管理后台**维持现有的 HTTP Basic Auth**（单管理员、账号来自环境变量）不动，两套鉴权完全分离——管理员不是账号，账号也进不了管理后台。JWT 的代价是签发后无法在服务端主动吊销（除非维护黑名单），对当前场景可接受：用短有效期 + 重新登录覆盖，比为吊销引入一张会话表更划算，这与 schema-full 里「后台会话不可服务端吊销、改用短时效签名」的取舍一脉相承。

> JWT 签名密钥走环境变量（如 `JWT_SECRET`），绝不入库、不进配置文件。密钥泄露等于令牌可伪造，这一点与仓库既有的「密钥一律环境变量注入」约定一致。

已排除的相邻选项：其一，改造 `users` 表加登录字段——被否，污染匿名 QQ 用户语义；其二，用服务端 session + cookie 替代 JWT——被否，多工具共享登录态时无状态令牌更省心，且仓库无现成的 session 存储；其三，注册就要求邮箱验证码（GopherAI 的做法）——被否，准入已由邀请码把关，验证码只是徒增依赖。
