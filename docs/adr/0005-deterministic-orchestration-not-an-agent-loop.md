# 受控一次性工具决策，不采用开放式 agent 循环

> 已被 ADR 0010 的双 Agent 工作流取代；本文保留为从单一搜索 Agent 演进的历史背景。

普通检索先由模型做一次受控工具决策：它必须且只能调用 `search_papers`，参数只有检索数量、`continue/refine/restart` 模式和是否排除本会话已展示论文。Go 校验参数后最多执行一次工具；模型不能决定重复搜索、不能访问数据库 ID，也不能接触 paperscraper/arXiv 的 HTTP、重试和 over-fetch 细节。

这个受限 Agent 解决自然语言控制问题，例如“再来 5 篇”必须表达为 `count=5, mode=continue, exclude_seen=true`，而不是把“5篇”编译成学术关键词。工具执行后，相关性判断、摘要总结、排序、完整 Abstract 长度控制、序号分配和持久化仍由固定 Go 流程完成。因此系统仍然没有开放式 ReAct 循环，单轮工具预算恒为 1，候选可归因、调用数和成本仍有固定上限。

| 提示词 | 职责 | 输出形态 | 思考模式 |
|---|---|---|---|
| P1 | 选择 `search_papers` 工具参数（一次） | Tool Call | 关 |
| P2 | 编译或细化检索规格 | JSON | 关 |
| P3 | 批量相关性判断（一次覆盖整批候选） | JSON | 关 |
| P4a | 单篇第一次快速精读（全文重点片段） | 文本 | 关 |
| P4b | 单篇第二次深度精读（完整全文） | 文本 | 开 |
| P5 | 多篇对比（上限 3 篇，重读全文） | 流式文本 | 开 |
| P6 | tldr 补生成 | 短文本 | 关 |

接口在 P1 使用 DeepSeek Function Calling，因为这里确实需要模型选择工具参数；运行时强制工具名为 `search_papers` 并校验 JSON，任意模型输出下工具调用次数都不超过一次。P2/P3 继续使用 JSON Output，它们只转换数据、不选择控制流。思考模式按调用性质分配：P1–P4a 高频、简单、要快，推理 token 是纯浪费；P4b/P5 低频且真需推理，而输出 token 单价是输入的四倍，只在用户明确要求第二次深度精读时支出。

P6 是唯一与用户方向无关的提示词，因此其结果全局缓存、跨用户跨方向复用（`papers.tldr`）。这是"速览"拆分的兑现点："这篇讲什么"是论文自身属性，算一次即可；"这篇与你的方向匹配吗"必须按方向计算，无法跨用户复用。

P3 的判断随候选列表一起落在 `messages.shown_papers` 里，并记下 `spec_version` 与提示词版本；要复用旧判断就查同方向、同规格版本、同提示词版本的最近一条，不单独建缓存表——缓存键既然含 `spec_version`，用户任何一次改规格都会击穿它，收益抵不上一张表。

P4a/P4b/P5 的结果**不做跨用户缓存**（ADR 0008 取消了 `analyses` 表）。第一次快速精读只发送已校验全文中的重点片段并关闭深度思考；用户确认值得继续后，第二次深度精读才把完整全文送入模型并开启深度思考。两次都带入当前检索规格，使分析贴合用户方向。

流水线中一半以上的步骤不经过模型：规则匹配指令与数字、宽度检测、CCF 等级匹配与别名归并、引用速度与同龄组百分位、质量档位判定、排序截断、全文质量校验、论文身份归并、限速排队、序号分配与展示记录写入。其中**全文质量校验是防幻觉的主闸门**——防幻觉依靠可判定的校验，而不是在提示词里写"不要编造"。

只有两处允许由用户闭合的迭代：继续检索必须由下一条用户消息触发新的、预算为 1 的工具调用；宽度或条件不清时输出追问后结束。工具自身可以为了满足 count 在 provider adapter 内有界 over-fetch，但模型不能根据结果再次调用工具。

已知边界：探索型需求（"帮我想个能出成果的方向"）在这个设计下体验很差，宽度检测会持续拒绝。这是取舍——本系统服务于"我知道自己在找什么方向"的用户。
