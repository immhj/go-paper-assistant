# Spec 0003 · 免费访客访问与邮箱验证

> **部分过时：** [ADR 0017](../adr/0017-research-projects-as-web-conversation-boundary.md) 将 Web 会话的直接归属改为研究项目，并将访客升级/导入扩展为完整项目转移；本文关于 `owner_account_id` / `owner_guest_id`、保留旧 Web 会话和直接转移会话的要求不再适用于研究项目实现，其余免费访问、身份、资格与安全要求继续有效。

> 状态：ready-for-agent
> 相关 ADR：[0016 免费产品、访客访问与邮箱验证](../adr/0016-free-guest-access-and-email-verification.md)（supersedes 0015，partially supersedes 0013/0014）。本文部分取代 Spec 0001/0002 的邀请码、邮箱、鉴权撤销、账号专属 Web 和额度要求；未冲突的单体架构、SSE、确定性编排和管理后台分层要求继续有效。
> 术语与边界：以 [`CONTEXT-MAP.md`](../../CONTEXT-MAP.md)、[平台术语表](../contexts/platform/CONTEXT.md)和[论文助手术语表](../../CONTEXT.md)为准。“访客”“账号”“用户”不得互换。

## 1. 目标与范围

交付一个可分阶段上线的免费平台入口：未登录浏览器凭三十天访客凭证使用 Web 聊天、检索和速览，并在该凭证周期内获得一次精读；注册人通过 QQ SMTP 六位邮箱验证码创建账号；账号可登录、重置密码并让旧 JWT 立即失效；访客可升级、选择向已有账号导入历史或主动清除数据；所有昂贵操作受安全限流、成本熔断和人工急停保护。

本 Spec 不实现 QQ 绑定、账号自助注销、修改邮箱、付费/会员、跨重启任务恢复、第二个工具或邀请码新功能。QQ 单聊继续使用论文助手“用户”身份和既有被动回复规则。

## 2. 规范性需求

以下“必须/不得”均为上线验收条件。

### R1. 免费产品与访问能力

1. 访客和账号的普通聊天、论文检索、速览不得设置产品次数额度；账号精读不得设置产品次数额度。
2. 每个访客凭证周期只能成功消费一次访客精读资格。执行前必须原子预留；成功保存有效结果后消费；系统失败且无可恢复有效结果时退还；客户端断线不退还。
3. 产品额度不得复用 QQ 被动回复计数、安全限流或成本预算字段/错误码。
4. Web 请求无账号 JWT 时按访客处理；JWT 存在但无效、过期、账号停用或 `auth_version` 不匹配时返回身份错误，不得降级成访客。

### R2. 访客凭证与隐私

1. 首次进入或首次调用访客 API 时签发 `guest_session` Cookie：至少 256 bit 随机熵、值不含业务信息，`HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`，生产环境还必须 `Secure`。
2. MySQL 只存凭证的 SHA-256 或更强摘要。访客凭证自签发起固定三十天过期，不滑动续期，不使用设备指纹。
3. 过期、清除、升级或导入完成的凭证必须被拒绝，并返回清除 Cookie 的响应；不得恢复其精读资格。
4. 页面必须清楚说明“访客记录最多保存 30 天”，并始终提供清除当前访客数据入口。

### R3. 注册与邮箱验证

1. 注册第一步接收规范化邮箱、昵称和密码，密码立即用 argon2id 哈希；明文密码不得进入 MySQL、Redis、日志、队列或邮件。
2. 待验证注册放 Redis，十分钟 TTL。验证码为密码学安全随机的六位数字，只存摘要；最多失败五次；同一邮箱六十秒内不得重发；成功重发后旧码失效。
3. 注册验证码通过专用个人 QQ 邮箱 SMTP 发送。默认连接 `smtp.qq.com:465` 并使用隐式 TLS，也可通过 `SMTP_TLS_MODE` 显式选择 QQ 支持的 STARTTLS；`SMTP_HOST`、`SMTP_PORT`、`SMTP_FROM`、`SMTP_AUTH_CODE`、`SMTP_TLS_MODE` 来自环境变量。必须使用 QQ 邮箱 SMTP 授权码而非登录密码，授权码不得输出。
4. 待验证注册不是账号。只有验证码正确且未过期时才在 MySQL 事务中创建账号、设置 `email_verified_at` 并完成可选访客升级。
5. 邮箱按统一规范化结果全局唯一；两个并发验证最多一个成功。注册不再接收、校验或消费邀请码。
6. 注册与密码重置验证码必须按 purpose 隔离；任一用途的验证码不得用于另一个用途。

### R4. 登录、JWT 与密码重置

1. 登录使用邮箱和密码。邮箱不存在、密码错误、邮箱尚未验证和账号停用的外部响应不得泄露可枚举细节；需要继续验证的已认证旧账号流程可在密码验证成功后返回专用状态。
2. JWT 至少包含稳定用户名、`auth_version`、签发/过期时间；鉴权必须读取当前账号状态和版本。
3. 密码重置请求无论邮箱是否存在均返回同样的 202 形状和近似时序；只给已验证且启用的账号发送邮件。
4. 重置码验证成功后，在一个 MySQL 事务中更新 argon2id 密码哈希并递增 `auth_version`。此前所有 JWT 在下一次请求时必须失败。
5. 管理后台继续使用 HTTP Basic Auth；Basic Auth 不能冒充账号，账号 JWT 不能进入 `/api/admin/*`。

### R5. 历史升级、导入与清理

1. 新账号由当前访客注册产生时，账号创建与访客会话转移必须在同一 MySQL 事务中完成；导入会话保持独立，不拼接消息、候选序号或展示记录，并成为账号当前会话。
2. 已有账号在浏览器带有效访客凭证登录时，前端必须询问是否导入。未明确确认不得转移；拒绝后访客历史保留至原到期时间。
3. 导入接口必须要求有效账号 JWT 和当前访客 Cookie，并支持幂等键；重复请求不得复制历史或重复消费资格。
4. 导入/升级成功后原访客凭证失效。访客尚未消费的精读资格不得变成账号额度；账号本来就没有产品次数额度。已预留中的任务不得导入，返回冲突直至任务结束。
5. 主动清除必须删除当前访客的会话、消息、展示记录与资格状态，并吊销凭证。短期 IP 安全限流键不删除。
6. 后台任务至少每日清理过期访客内容；批处理必须可分页、可重试、幂等，并记录删除数量与失败，不记录消息正文。

### R6. 安全限流与成本熔断

1. Redis 原子执行以下默认限制：每主体同时最多一个模型任务；普通聊天每分钟十次；检索/速览每分钟三次；账号精读每分钟两次；每 IP 每分钟三十个 API 请求；登录连续失败五次后逐步延迟并在十五分钟无失败后恢复。
2. 验证码还必须限制同邮箱六十秒重发、同流程五次验证，并配置每 IP、每邮箱、全局邮件发送窗口；具体邮件窗口可运行配置调整，但不得弱于重发限制。
3. 所有模型与论文处理操作在开始前检查全局成本窗口。默认每小时 2 美元、每日 10 美元；任一达到后拒绝新的昂贵操作。注册、登录、验证码校验、历史读取、清除和后台不受影响。
4. Redis 不可用时，验证码、访客昂贵操作和新的检索/速览/精读失败关闭；邮箱密码登录及已有账号的资料/历史读取在 MySQL 可用时继续服务。
5. 成本事件持久写 MySQL，Redis 维护原子窗口聚合；窗口可从 MySQL 重建。成本状态未知或 Redis 不可用时，新的昂贵操作失败关闭。
6. 安全限流、访客资格不足、成本熔断和人工急停分别使用 `RATE_LIMITED`、`GUEST_DEEP_READ_EXHAUSTED`、`COST_BREAKER_OPEN`、`EMERGENCY_STOPPED`，不得混用。

### R7. 上线开关

服务端必须支持并在管理后台只读展示：

- `PLATFORM_OPEN_REGISTRATION_ENABLED`
- `PLATFORM_GUEST_ACCESS_ENABLED`
- `PLATFORM_GUEST_DEEP_READ_ENABLED`
- `PLATFORM_GUEST_IMPORT_ENABLED`
- `PLATFORM_EMAIL_VERIFICATION_REQUIRED`
- `PLATFORM_COST_BREAKER_ENABLED`

生产最终状态必须要求邮箱验证并启用成本熔断。开关关闭只阻止新动作，不得删除或破坏已有账号、访客记录和任务结果。客户端不得覆盖开关。人工急停优先级最高，其次成本熔断、安全限流、产品资格、业务执行。

## 3. API 契约

所有 JSON 错误沿用 `{ "error": "...", "status": "ERROR_CODE" }`；错误消息可本地化，客户端只依赖 `status`。除 SSE 外响应为 `application/json`。改变状态的 Cookie API执行既有同源/请求标记与 CSRF 防护；日志不得写 Cookie、JWT、密码、SMTP 授权码或验证码。

### 3.1 会话与访客

- `GET /api/session`
  - 无账号 JWT 且无有效 Cookie：若 `PLATFORM_GUEST_ACCESS_ENABLED=true`，创建访客并设置 Cookie。
  - 返回 `{actorType:"guest|account", account?, guest:{expiresAt, deepReadState}?, features:{...}}`。
  - 无效 JWT：`401 INVALID_TOKEN`，不签发访客凭证。
- `DELETE /api/guest`
  - 需要有效 `guest_session`，返回 `204` 并清 Cookie。
- `POST /api/guest/import`
  - 需要有效账号 JWT、有效访客 Cookie 和 `Idempotency-Key`，请求 `{confirm:true}`。
  - 成功返回 `{importedConversationIds:[...], currentConversationId}` 并清 Cookie。
  - 无待导入历史返回幂等成功；资格预留中返回 `409 GUEST_TASK_IN_PROGRESS`。

### 3.2 注册

- `POST /api/register/code`
  - 请求 `{email,nickname,password}`；返回 `202 {registrationToken,expiresAt,resendAfter}`。
  - 再次调用同一接口即为重发；服务端执行六十秒冷却，新码成功发送后废止旧码。
- `POST /api/register`
  - 请求 `{registrationToken,code}`；成功返回 `201 {token,account,guestUpgrade}`，其中 `guestUpgrade` 说明是否转移当前访客历史，并清除已升级 Cookie。
  - 错码 `400 VERIFICATION_CODE_INVALID`；过期 `410 VERIFICATION_EXPIRED`；尝试耗尽 `429 VERIFICATION_ATTEMPTS_EXHAUSTED`；并发邮箱冲突 `409 EMAIL_ALREADY_REGISTERED`。

### 3.3 登录与重置

- `POST /api/login`
  - 请求 `{email,password}`；成功返回 `200 {token,account,guestImportAvailable}`。
  - 所有普通凭证失败统一 `401 INVALID_CREDENTIALS`；限流返回 `429 RATE_LIMITED`。
  - `guestImportAvailable=true` 时前端必须询问，登录本身不自动导入。
- `POST /api/password-reset/code`
  - 请求 `{email}`；始终返回 `202 {resetToken,expiresAt,resendAfter}` 的同形响应。不存在的邮箱使用不可验证的伪流程句柄，后续统一失败；再次调用即按冷却规则重发。
- `POST /api/password-reset`
  - 请求 `{resetToken,code,newPassword}`；成功 `204`，递增 `auth_version`。验证码错误/过期/耗尽不得说明邮箱是否存在。
- `GET /api/me`
  - 需要账号 JWT，返回账号公开字段与当前验证状态，不返回密码哈希或版本内部值。

### 3.4 Web 聊天

Spec 0002 的 HTTP + SSE、逐帧 JSON、`[DONE]`、工具进度和通道无关编排继续有效，但 handler 接受“有效账号 JWT”或“有效访客 Cookie”。访客精读在启动执行前返回资格状态；成功预留后 SSE 断开不自动取消或退还。错误帧必须包含稳定 `status`，最终资格由服务端查询恢复，不能由前端猜测。

## 4. 数据模型与存储分工

字段名可按仓库命名惯例微调，但约束和状态机不得改变。

### 4.1 MySQL（持久事实）

1. `accounts`：保留 `username`、`email`、`nickname`、`password_hash`、可空唯一 `qq_openid`、`status`；新增可空 `email_verified_at DATETIME(3)`、`auth_version BIGINT NOT NULL DEFAULT 1` 与 `active_conversation_id`。新账号的 `email_verified_at` 必须非空；历史账号保持可空以支持无损迁移。`email` 使用规范化值与唯一键；删除 `invited_by_code`。
2. `guest_sessions`：`id`、唯一 `token_hash`、`status(active|upgraded|cleared|expired)`、`deep_read_state(available|reserved|consumed)`、可空 `reservation_id/reserved_at`、`expires_at`、可空 `upgraded_to_account_id`、时间戳。只有 `active` 且未过期可用。
3. `conversations`：增加可空 `owner_guest_id`，与 QQ `user_id`、账号 `owner_account_id` 构成“恰有一个所有者”的约束或等价的受测事务不变量；为三种归属查询建索引。
4. `cost_events`（若现有成本明细表可满足则复用）：记录发生时间、操作种类、主体类型/匿名审计标识、估算或最终成本、关联任务，支持小时/日窗口重建；不得记录消息正文。
5. 导入不建消息副本：事务内更新会话所有者和当前会话指针，记录幂等键/导入审计。删除访客时依既有外键顺序删除消息、展示记录、会话和访客资格。

### 4.2 Redis（短期状态）

1. `verification:registration:<token>`：规范化邮箱、昵称、密码哈希、验证码摘要、失败次数、发送代次，TTL 十分钟。
2. `verification:reset:<token>`：账号引用、验证码摘要、失败次数、发送代次，TTL 十分钟；与注册 key 完全隔离。
3. `cooldown:*`、`ratelimit:*`、`concurrency:*`：重发冷却、安全限流与有界并发租约，均有 TTL，释放操作须校验租约 token。
4. `cost:hour:*`、`cost:day:*`：成本窗口聚合；写入必须与 MySQL 成本事件采用可重放/补偿策略，重建期间昂贵操作失败关闭。

Redis 不得保存长期会话、消息、账号事实、访客精读最终状态或唯一的成本明细。

## 5. 错误与故障语义

| 场景 | 外部行为 | 状态/恢复 |
|---|---|---|
| MySQL 不可用 | 依赖身份、历史、资格或写入的请求返回 503 | `DEPENDENCY_UNAVAILABLE`；不得签发可用访客或宣称注册成功 |
| Redis 不可用 | 验证码、访客昂贵操作和新的检索/速览/精读返回 503 | 失败关闭；邮箱密码登录及已有账号资料/历史读取在 MySQL 可用时继续 |
| QQ SMTP 拒绝/超时 | 注册/重置发送返回 503，可重试 | `EMAIL_DELIVERY_UNAVAILABLE`；失败发送对应验证码不可验证，账号不创建 |
| 验证码错误 | 计一次失败，不延长 TTL | 五次后流程锁定；新 resend 流程产生新代次 |
| Cookie 过期/吊销 | 清 Cookie，普通访客请求可按开关创建新凭证 | 不恢复旧历史或资格；短期 IP 限流保留 |
| 访客资格已预留 | 重复精读返回 409 | `GUEST_DEEP_READ_IN_PROGRESS`，客户端查询已有任务/结果 |
| 资格已消费 | 精读返回 403 | `GUEST_DEEP_READ_EXHAUSTED`，普通功能仍可用 |
| 成本阈值达到或状态未知 | 新昂贵操作返回 503 | `COST_BREAKER_OPEN`，可返回窗口恢复时间；廉价控制面继续 |
| 人工急停 | 按 ADR 0011 拒绝新工作 | `EMERGENCY_STOPPED`，优先于其他执行检查 |
| SSE 断线 | 后端任务按既有进程内规则继续或结束 | 已保存有效结果则消费；纯系统失败且无有效结果才退还 |
| 导入重复提交 | 返回首次结果或无变化成功 | 幂等，不复制、不拼接 |

对外响应不得包含 SQL、Redis key、SMTP 详情或内部堆栈。`Retry-After` 用于明确可恢复的 429/503。

## 6. 迁移与历史数据

1. 新增向前迁移，不修改已发布的 `0006`/`0007`；无论旧迁移是否已应用，迁移都必须可在当前 schema 上安全执行，并同步更新 `docs/schema.sql`/`docs/schema-full.sql`（实现阶段）。
2. 先新增可空列与新表/索引，再回填/校验，再启用新写路径，最后收紧约束；大表变更须避免长时间锁表。
3. 已存在账号不得被自动标记为“邮箱已验证”。密码验证成功后进入一次性旧账号邮箱验证流程；过渡期可由上线开关维持旧登录，但生产验收前必须关闭旁路。完成验证后写 `email_verified_at`，不改变稳定用户名和历史归属。
4. 完整删除 `invite_codes` 表、`accounts.invited_by_code` 字段、相关索引，以及邀请码接口、服务、DAO 和后台页面；迁移前备份需要留存的历史准入数据。新注册流程不得再读取或写入邀请码。
5. 若已有账号 Web 会话，保持 `owner_account_id` 不变；QQ 会话保持 `user_id`。不得把任何历史会话猜测性地归给访客。
6. 过期访客清理任务在删除前按 `expires_at` 分批选择，先吊销后删内容；故障重跑结果相同。清理指标包含扫描、删除、跳过在途任务和失败数量。
7. 回滚应用版本时保留新增 schema 和数据；功能开关关闭新入口。不得通过回滚删除账号、访客历史、`auth_version` 或验证记录。

## 7. 前端要求

1. 继续使用仓库的静态 HTML/CSS/JS、零构建风格。初始化先调用 `/api/session`，根据 `actorType`、资格状态和服务端 features 渲染，不从 Cookie 内容推断身份。
2. 访客可以直接聊天、检索、速览；精读入口明确显示“一次/30 天”的可用、进行中或已使用状态，不把安全限流文案写成产品额度。
3. 注册 UI 包含邮箱、昵称、密码、六位码、十分钟倒计时、五次尝试提示和重发倒计时；不得出现邀请码输入框。
4. 登录后若 `guestImportAvailable=true`，显示“导入访客记录/暂不导入”明确选择，默认不导入。注册升级结果要说明会话已作为独立会话转移。
5. 提供忘记密码流程；重置成功后清除本地 JWT 并回登录页。收到 `INVALID_TOKEN`/版本失效时也必须清理 JWT，不降级隐藏错误。
6. 访客数据说明与清除入口可从聊天页直接到达；清除前确认，成功后清空本地展示并由服务端吊销 Cookie。
7. 对 `RATE_LIMITED`、资格耗尽、成本熔断、人工急停、邮件故障分别显示可行动且不泄密的文案；SSE 断线后重新拉取服务端会话/资格状态。

## 8. 管理后台与运行配置

1. 保持“平台/论文助手”一级、域内二级的信息架构。平台 › 账号显示邮箱、昵称、创建时间、邮箱验证时间/待验证状态、启用状态；不得显示密码哈希。
2. 邀请码从主导航、接口和持久化结构完整移除。迁移前需要留存的历史准入数据应单独备份，不继续作为运行时产品能力。
3. 平台运行状态只读展示六个上线开关、Redis/SMTP 健康、小时/日成本与阈值、熔断状态、邮件发送/限流指标、访客数量与过期清理结果。敏感配置值必须掩码，SMTP 授权码永不返回。
4. 管理员禁用账号后其 JWT 下一次请求即失败；若提供“使所有设备退出”，通过递增 `auth_version` 实现并留审计。
5. 既有论文助手概览、用户与会话、运行设置和人工急停不得回归；成本熔断与人工急停要分开展示。

## 9. 测试要求

### 9.1 单元/契约测试

- Cookie 随机性、摘要存储、固定三十天过期、属性与吊销；无 JWT/无效 JWT 分支。
- 验证码固定六位、十分钟 TTL、五次失败、六十秒重发、新码废旧码、purpose 隔离、日志脱敏。
- 同邮箱并发验证只创建一个账号；待验证状态不产生账号；SMTP 失败不留下可用验证码。
- argon2id 注册/登录/重置；重置递增 `auth_version`，旧 JWT 失败、新登录成功。
- 访客精读 `available → reserved → consumed` 与系统失败退还；并发请求只有一个预留成功；断线不错误退还。
- 注册升级、登录确认导入、拒绝导入、幂等重试、在途任务冲突、清除和过期批量清理。
- 每一类安全限流边界和窗口恢复；产品额度、限流、熔断、急停错误码隔离。
- 成本小时/日任一达阈值时拒绝；Redis 重建/故障时昂贵操作失败关闭，控制面仍可用。
- 六个开关每种关闭行为不删除数据，客户端参数不能绕过。

### 9.2 集成测试

- 真实 MySQL 验证唯一键、条件更新、资格原子性、账号创建 + 访客升级事务回滚、三类会话所有者和级联清理。
- 真实 Redis 验证 TTL、原子限流、并发租约、验证码代次和成本窗口重建。
- SMTP 使用 fake server 验证 TLS/认证配置、收件人与模板、超时/拒绝；CI 不向真实 QQ 邮箱发信。
- `httptest` 覆盖所有 API 状态、Cookie、CSRF/请求标记、Basic/JWT 隔离、反枚举响应和 `Retry-After`。
- 通道无关回合 seam 与 SSE 覆盖访客和账号，确保 QQ sink 行为及四次被动回复限制不回归。
- 静态前端 smoke test 覆盖访客首访、一次精读、注册验证、登录导入选择、密码重置、清除和各故障提示。

### 9.3 安全测试

- Cookie/JWT/验证码/密码/SMTP 授权码不出现在日志、错误、HTML 或管理 API。
- 验证码重放、跨 purpose、并发 resend、邮箱枚举、暴力登录、伪造/篡改 JWT、固定访客凭证、CSRF 清除/导入均失败。
- 清 Cookie/重复清除/重新签发不能恢复资格或绕过 IP 限流；访客只能读取自己的历史，账号不能导入他人的访客凭证。

## 10. 上线顺序与验收标准

### 10.1 上线顺序

1. 备份并演练向前迁移；部署 MySQL schema、Redis、成本事件与后台只读观测，所有新入口关闭。
2. 配置 QQ SMTP、JWT 和 Cookie 密钥，使用测试邮箱完成投递/退信演练；启用 `PLATFORM_EMAIL_VERIFICATION_REQUIRED` 与 `PLATFORM_COST_BREAKER_ENABLED`。
3. 先开放邮箱注册/重置给内部流量；验证反枚举、旧账号过渡和旧 JWT 撤销。
4. 小比例开启访客普通聊天/检索/速览；观察限流、Redis、成本和清理指标。
5. 开启访客导入，再开启一次精读；验证原子资格和失败退还。
6. 全量开启并验证后执行邀请码结构删除迁移；保留快速关闭访客、精读、导入、开放注册的能力。回滚只关开关/回退应用，不删除新增业务数据。

### 10.2 必须全部满足的验收标准

- 新浏览器无需注册即可获得安全 Cookie，并完成聊天、检索、速览；同一凭证并发精读最多一个成功，三十天周期内第二次被明确拒绝。
- 账号可无限次发起精读产品请求，但实测仍受并发、每分钟两次、安全限流、成本熔断和人工急停约束。
- QQ SMTP 六位码完成注册；过期、第五次后、60 秒内重发、旧码和跨用途码均按契约失败；邮件故障绝不创建账号。
- 密码重置后所有已签发旧 JWT 立即失败；管理后台 Basic Auth 与账号 JWT 保持隔离。
- 新注册自动升级当前访客历史；已有账号登录必须选择后才导入；导入保持独立会话且重复提交无副本。
- 主动清除与到期清理删除访客内容并吊销凭证，重新签发不解除 IP 限流；清理任务可安全重跑。
- 达到 2 美元/小时或 10 美元/日阈值后，新昂贵操作停止，而登录、验证、历史、清除和后台继续工作；Redis/成本状态未知时不放行昂贵操作。
- 六个服务端开关均经生产式配置演练；最终邮箱验证与成本熔断开启，邀请码接口、代码、后台页面、表和账号邀请字段均已删除。
- 旧 Spec 0001/0002 中未被替代的后台分层、SSE、确定性编排和 QQ 回归测试通过；所有新增单元、集成、安全与 smoke 测试通过。
- 发布后观测至少覆盖：注册/验证成功率与邮件失败率、限流命中、访客资格状态、导入/清理结果、成本窗口/熔断和依赖健康；告警不包含敏感数据。
