# Spec 0001 · 平台基座：账号、邀请码、鉴权与后台重构

> **Partially superseded：** [Spec 0003](0003-free-guest-access-email-verification.md) 与 [ADR 0016](../adr/0016-free-guest-access-and-email-verification.md) 取代邀请码准入、不验证邮箱、JWT 无即时失效及“不做限流/熔断”的要求；未冲突的账号拆分、argon2id、管理后台分层和鉴权隔离仍有效。本文原 `ready-for-agent` 状态仅作历史记录，不得脱离 Spec 0003 独立执行。

> 状态：ready-for-agent（本仓库暂未配置 issue tracker，spec 以文件形式留存在 `docs/specs/`；配置 tracker 后可迁移并打 `ready-for-agent` 标签）。
> 相关 ADR：0012（转向工具集平台）、0014（账号身份 + JWT）、0015（邀请码准入）。术语见 `docs/contexts/platform/CONTEXT.md`。

## Problem Statement

项目现在只有一条入口：QQ 单聊。用户是匿名的 QQ 标识，没有登录身份，也没有任何准入控制——谁把机器人加进 QQ 谁就能用。我想把它做成一个面向研究生的工具集平台，论文助手是第一个工具。要做到这一步，首先缺三样东西：一个有凭证的登录身份、一个能控制“谁能进来”的准入手段、以及一个能在多个工具间共享的登录态。同时现有的管理后台是围绕论文助手一个工具做的（概览 / 用户与会话 / 运行设置），它需要升级成能管理整个平台的后台，第一件要管的事就是发邀请码。

## Solution

在论文助手之上新增一个平台层，对用户提供：

- **凭邀请码注册**：没有有效邀请码不能创建账号。注册填邮箱、昵称、密码、邀请码；系统为账号生成一个用户不可见的内部用户名作为归属键。
- **邮箱 + 密码登录**，登录成功换取一个携带用户名的 JWT，后续请求带着它访问受保护接口。
- **管理后台升级为研究生工具管理后台**：导航从平铺的三项，重构成“一级（工具 / 平台域）+ 二级（域内页面）”两层。原有的概览 / 用户与会话 / 运行设置整体降为“论文助手”一级之下的二级页；新增“平台”一级，下辖“邀请码”和“账号”两个二级页。管理员在“平台 › 邀请码”里生成邀请码、设置使用次数与有效期、查看每张码的消费情况。

管理后台自身的鉴权维持现有的 HTTP Basic Auth（单管理员、来自环境变量），与平台用户的 JWT 完全分离。

## User Stories

1. 作为一个拿到邀请码的研究生，我想用邮箱、昵称、密码加邀请码注册一个账号，以便登录平台使用工具。
2. 作为一个没有邀请码的人，我在注册时得到“需要有效邀请码”的明确拒绝，以便我知道要先去要一张码。
3. 作为一个注册用户，我想用邮箱和密码登录，以便进入平台。
4. 作为一个登录失败的用户，我想在邮箱不存在、密码错误、账号被禁用时都得到不泄露具体原因的登录失败提示，以便账号信息不被探测。
5. 作为一个已登录用户，我想在后续请求里凭 JWT 被识别，以便访问只对我可见的数据，而无需每次重新登录。
6. 作为一个用了过期或已用满邀请码的人，我在注册时被拒绝，以便邀请码的额度和有效期被真正执行。
7. 作为一个用了错误邀请码的人，我的这次失败尝试不会消耗任何一张码的额度，以便无效尝试不会把别人的码悄悄耗光。
8. 作为一个用了同一个邮箱二次注册的人，我得到“邮箱已被注册”的拒绝，以便邮箱的唯一性得到保证。
9. 作为一个账号，我可以随时修改昵称而不影响我已产生的任何数据归属，以便展示名和内部归属键解耦。
10. 作为管理员，我想在“平台 › 邀请码”页生成一张邀请码，以便发给我想邀请的人。
11. 作为管理员，我想在生成邀请码时设置使用次数（1 即一次性，大于 1 即多人共享），以便一张码可以发给一个课题组。
12. 作为管理员，我想在生成邀请码时设置可选的有效期，以便过期后自动失效。
13. 作为管理员，我想看到每张邀请码的已用次数 / 总次数、是否过期、生成时间，以便判断哪些码还能用。
14. 作为管理员，我想在“平台 › 账号”页看到账号列表，包括邮箱、昵称、注册时间、准入来源（用了哪张邀请码），以便知道每个人是谁邀来的。
15. 作为管理员，我想禁用一个账号，以便被禁用的账号无法再登录。
16. 作为管理员，我想在同一个后台里既能管平台级的邀请码和账号，又能进到“论文助手”一级看原有的概览 / 用户与会话 / 运行设置，以便一个后台管所有工具。
17. 作为管理员，我打开一个书签直达某个二级页（如 `#platform/invites`）时，后台能正确定位到该页，以便深链可用。
18. 作为平台维护者，我想让 JWT 的签名密钥来自环境变量，以便密钥不进代码库、可按部署轮换。
19. 作为平台维护者，我想让账号密码以 argon2id 哈希存储，以便数据库泄露时明文密码不外泄。
20. 作为后续工具的开发者，我想复用平台已有的账号身份和登录态，以便接入新工具时不必再造一套用户系统。

## Implementation Decisions

- **新增平台数据表**：`accounts` 与 `invite_codes`，DDL 已在 `docs/migrations/0006_platform_accounts_invite_codes.sql`。`accounts` 三字段身份——`username`（系统生成、唯一、不可见、归属键）、`email`（登录凭证、唯一）、`nickname`（展示、可改）——加 `password_hash`、`invited_by_code`、可空唯一 `qq_openid`、`status(active|disabled)`。`invite_codes` 有 `max_uses` / `used_count` / 可空 `expires_at` / `created_by`。
- **持久化 seam 用独立接口**：不往 `dao.Store`（已很大且是论文助手专属）里堆平台方法，新增一个平级接口 `PlatformStore`（账号 CRUD、按邮箱/用户名查账号、邀请码生成/列表/原子消费），由同一个 MySQL store 实现。这样论文助手的持久化接口保持聚焦，平台测试也能对着一个小接口打桩。
- **邀请码消费必须原子**：注册在事务里用条件更新 `UPDATE invite_codes SET used_count = used_count + 1 WHERE code = ? AND used_count < max_uses AND (expires_at IS NULL OR expires_at > NOW(3))`，受影响行数为 1 才算占用成功；随后写入 `accounts` 并回填 `invited_by_code`。整个注册是一个事务，任一步失败回滚，不留下“码被占用但账号没建成”的空洞。使用次数只统计成功注册，校验失败不消费额度（ADR 0015）。
- **用户名生成**：系统生成，全局唯一、稳定、用户不可见。生成策略（如随机短串或雪花）由实现选择，但一经分配不再变更。
- **鉴权 seam**：HTTP 层是单一 seam——`router.New` 返回的 `http.Handler`。新增平台 API 分组（注册、登录，以及管理员生成/查询邀请码、查询/禁用账号），复用现有 `writeJSON` / `writeError` 与 Go 1.22 mux 的方法+路径注册风格。新增一个 `jwtAuth` 中间件，形态对齐现有 `basicAuth`：校验 `Authorization: Bearer <token>`，解出用户名注入请求 context 供后续处理器使用。用户身份**只从 context 取，绝不作为业务参数**接受。
- **JWT**：令牌 claim 至少含用户名与过期时间；签名密钥来自环境变量（如 `JWT_SECRET`），启动时缺失且非开发环境应拒绝启动。无服务端吊销，用短有效期 + 重新登录覆盖（ADR 0014）。
- **管理员接口归属管理后台鉴权**：生成邀请码、查询账号等管理操作走现有 Basic Auth 保护的 `/api/admin/*` 分组，`created_by` 记录管理员用户名。平台用户的 JWT 不能访问这些接口。沿用现有的 `X-Requested-With` 标记防跨站表单提交约定（见 `rejectUnmarked`）。
- **管理后台前端重构**：`web/admin/index.html` 从三项平铺导航改为两层结构。一级：`平台`、`论文助手`。`平台` 下二级：`邀请码`、`账号`；`论文助手` 下二级：`概览`、`用户与会话`、`运行设置`（即现有三视图，逻辑不变，只是收进一级之下）。沿用现有的纯静态、零构建、hash 路由风格，深链形如 `#paper/overview`、`#platform/invites`。标题栏一级名 + 二级名。
- **不引入前端框架**：静态 HTML/CSS/JS，观感对齐 GopherAI-v2（ADR 0012）。注册 / 登录页作为平台面向用户的入口，同样是静态页。
- **API 契约（形状，非路径定死）**：注册接收 `{email, nickname, password, inviteCode}`，成功返回账号公开信息（不含密码哈希）或直接返回登录态；登录接收 `{email, password}`，成功返回 `{token, ...账号公开信息}`。生成邀请码接收 `{maxUses, expiresAt?}`，返回码明文与元数据。所有错误走现有 `{error, status}` 形状。

## Testing Decisions

- **好测试只验外部行为**：对着 HTTP 处理器和 `PlatformStore` 接口的可观察结果断言，不断言私有函数、SQL 文本或字段命名等实现细节。
- **主 seam：HTTP handler（httptest）**。用 `router.New` 组装真实路由 + 真实中间件，注入一个 fake `PlatformStore`，用 `httptest` 驱动，覆盖：
  - 有效邀请码注册成功、`used_count` 自增、账号 `invited_by_code` 正确回填；
  - 邀请码错误 / 已用满 / 已过期分别被拒，且**不消费任何额度**；
  - 一次性码第二次注册被拒；
  - 重复邮箱被拒；
  - 登录成功返回可用 JWT；邮箱不存在 / 密码错 / 账号禁用均返回不区分原因的失败；
  - 带合法 JWT 通过 `jwtAuth`、无 / 过期 / 篡改 token 被拒；
  - 管理员邀请码 / 账号接口在 Basic Auth 缺失或 `X-Requested-With` 缺失时被拒。
- **并发原子性**：针对邀请码消费，测并发注册同一张 `max_uses=1` 的码只有一个成功（可在 store 层用真实 MySQL 或对条件更新的行为契约做集中测试）。
- **prior art**：仓库当前**没有任何测试**（无 `_test.go`，`cmd/smoke/` 为空）。本 spec 建立第一个测试 seam。测试就近放在 controller / service 包内，fake store 放在测试包或一个 `internal/dao` 下的测试辅助里，供后续工具复用。

## Out of Scope

- **Web 聊天通道**（论文助手在网页里对话）——见 Spec 0002。
- **QQ 绑定的用户操作流程**：`accounts.qq_openid` 列本 spec 建好，但“把账号绑定到 QQ 身份”的交互与合并视图不在本期。
- **找回密码 / 邮箱验证码 / 改邮箱**：注册不做邮箱验证码（ADR 0014），找回密码留待后续。
- **第二个及以后的工具**：导航结构为其预留（多一个一级项即可），但不实现任何新工具。
- **账号级限流、成本熔断**：沿用现状不做。
- **邀请码的批量生成、撤销、多次可用之上的更复杂配额**：`max_uses` 已覆盖多次可用；撤销/批量非本期。

## Further Notes

- 管理后台与平台用户是两套鉴权，实现时务必不要让 JWT 能进 `/api/admin/*`，也不要让 Basic Auth 冒充账号。
- `accounts.qq_openid` 唯一键允许多个 NULL（MySQL 行为），未绑定的多账号不冲突。
- 新增环境变量 `JWT_SECRET`（及可选的 JWT 有效期配置）应补进 `.env.example` 与配置加载；生产缺失应快速失败。
- 后台导航重构会改动 `web/admin/index.html` 的视图切换逻辑，注意保持现有三视图（概览 / 用户与会话 / 运行设置）的加载与图表逻辑不回归。
