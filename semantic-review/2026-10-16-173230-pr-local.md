# Bounded plan execution: one planner call, up to 3 steps on the Web

The change replaces the Router + Executor model pair with a single JSON planner call (`planTurn`) that returns `respond | clarify | plan`, validates the plan in Go against the ADR 0021 transition table, and runs it step by step in `executePlan`. Steps reference the first search's displayed list through two Go-resolved selectors (`top_relevance(k)`, `position(n…)`), and plan-capable tools report success through a context mark so that "needs user action" outcomes stop the plan. QQ goes through the same planner with `maxSteps=1`. The trace moves to version 3 with a per-step `plan` array, and the admin tool distribution counts steps via `JSON_TABLE`. Builds, `go vet` and `go test ./internal/service/` pass.

Watch for: a failing step (as opposed to a stopping one) never tells the user which later steps were skipped (confirmed); per-step quota and guest-reservation refusals at step 2+ end the turn as an error rather than a stop (confirmed); in multi-step plans the IEEE/arXiv source choice reads only the text before the first comma (confirmed); the `比较` keyword matches the adverb "比较新的", which lets a model-added comparison through the heavy-step gate (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

A plan is validated as a whole before any step runs. Multi-step plans also have every step's arguments strictly parsed, so a malformed later step is rejected before step 1 runs. No path was found that executes a prefix of a plan the validator should have rejected. The gap is in the validator's inputs: the deep-read/compare keyword gate reuses `sourceMention`, whose keyword and negation lists misread common phrasings.

Success marks sit only at the real success returns of search, abstract, read, compare and research answer. Expected-state returns (zero results, source quota, missing full text, unknown ordinal, model not configured) leave the step unmarked, so it becomes `stopped` with a not-run note. Failures are handled differently: a returned error ends the plan without the note. Gate refusals (rate limit, guest read already used) take this failure path, although the ADR lists 额度不足 as a stop.

Selectors resolve against the Web rendering (`reply.Web.Shown`), and the delivered context replaces the in-memory conversation context, so later steps see the new ordinals. Locks are per tool and never held across steps. Ordinal mappings are append-only, so a concurrent turn slipping in between steps (possible only without `webGuard`) cannot make the snapshot point at the wrong paper.

QQ keeps one step. Tool cost goes into the user-message cost only on failure, because bot messages carry it on success. Two behaviour changes reach QQ: through the shared validator, compare and deep read now need the user's literal keyword. Single-step plans with invalid arguments still fail as a task, which on QQ means no reply at all.

Per-step usage sums exactly to `toolUsage`, and the planner call is in `routerUsage`. The admin tool distribution attributes only tool cost to v3 steps but the whole turn cost to legacy rows, so per-tool cost is not comparable across the version boundary.

<summary>Issues (9)</summary>

1. **Failed step gives no not-run note** (medium, confirmed) — `plan_exec.go:108-111`, `:88-97` return the error without telling the user which steps didn't run, which contradicts ADR 0021 §7 and the 步骤 glossary. Deliver `notRunNote(rest)` (best-effort, joined with the error) before returning.
2. **Quota/reservation refusal is a failure, not a stop** (medium, confirmed) — `web_gate.go:70-73` (`AllowTool`) and `:99-101` (`ReserveGuestDeepRead`) errors at step ≥2 end the Web turn with `WebStatusError`. A guest plan with two reads always hits this on the second read. Classify `ErrRateLimited` / `ErrGuestDeepReadExhausted` / `ErrGuestTaskInProgress` raised by the gate as a stop with an explanation and the not-run note.
3. **Source selection reads only the search segment** (medium, confirmed) — `plan_exec.go:102` replaces `input.Content` and `search.go:49` passes it to `searchSource`, so "找联邦学习论文，只要 IEEE 的，然后对比…" searches arXiv. ADR §11 limits segmentation to count/continue overrides; pass the full text to `searchSource` (e.g. carry the segment separately for `parseToolCall` only).
4. **`比较` keyword false positive** (medium, likely) — `plan.go:76` accepts "比较" anywhere, including the adverb in "比较新的论文", so a model-added `compare_papers` passes the decision-5 gate. Drop bare "比较" or require a verb form ("比较一下", "比较第", "和…比较").
5. **Negation list misses common forms** (low, confirmed) — `sourceNegations` lacks "不需要", "无需", "别", "不" alone, so "不需要对比" counts as an affirmative request. Extend the list used for heavy-step keywords.
6. **QQ silent on invalid single-step arguments** (low–medium, confirmed behaviour; regression vs old flow not verifiable without git) — single-step plans skip `parseToolCall` in validation (`plan.go:218`), and the error from `executeToolCall` reaches `handleQQ` → `runUserWorker`, which only logs. Reply with a clarification, or parse single-step args in `validatePlan` and turn errors into a clarify on QQ.
7. **`readCommitted` is deliverer-wide** (low, likely) — `web_gate.go:104` checks a flag set by any earlier step, so a later guest read that reserved but failed would skip `FinishGuestDeepRead` and leave the reservation stuck. Today the second reservation is refused first, which hides this. Reset `readCommitted`/`guestReservationID` per step (e.g. in `beginStep` or when the gate reserves).
8. **Weak-relevance note is a separate message sent before the gate** (low, confirmed) — `plan_exec.go:93-97` posts "仍按你的要求继续…" as its own bubble before `BeforeTool`, so a quota refusal follows a promise to continue, and the step has two outgoing messages (glossary says the note belongs in the result). Fold the note into the step's output or send it after the gate passes.
9. **Missing tests for the risky paths** — no test covers mid-plan failure, gate refusal at step 2, guest multi-read, IEEE mention after the boundary, read/compare stop marks (full text unavailable), or `handleQQ` through `planTurn`.

<summary>Details</summary>

### Heavy-step keyword gate

The gate for decision 5 is `userRequests` → `sourceMention`, which counts a keyword as affirmative unless a phrase from `sourceNegations` immediately precedes it (`plan.go:75-89`). Two failure cases, both confirmed by reading the code:

```
"找几篇比较新的联邦学习论文，快速精读第一篇"   → "比较" affirmative → model-added compare_papers passes
"不需要对比，快速精读最相关的"                 → "不需要" not in list → affirmative
```

The first is the more serious one. "比较" meaning "fairly" is common in research requests, and decision 5 exists to stop the model adding a thinking step. Planner prompt guidance makes this less likely but does not replace the gate.

### Stop vs failure in `executePlan`

The stop path (`plan_exec.go:112-118`) marks the step `stopped`, leaves later steps `skipped`, and tells the user "上一步没有完成，以下步骤没有执行：…". The failure path (`:108-111`, plus the selector arg/note failures at `:88-97`) only sets `failed` and returns. The tools deliver their own failure text ("论文检索失败，请稍后重试"), but nothing says that steps 2-3 were dropped. On the Web the turn then emits a generic `WebStatusError` below the visible step-1 results.

Gate refusals take the failure path. `BeforeTool` runs inside `executeToolCall`, so a refusal comes back as a step error: `ErrRateLimited` from `AllowTool` (accounts get `ToolAccountDeep` on both quick and deep reads), or `ErrGuestDeepReadExhausted` from `ReserveGuestDeepRead`. Earlier steps are kept, as the glossary requires. The user, though, sees "请求过于频繁" or "本访客会话的精读资格已使用" as a turn error, with no list of skipped steps. For guests this is deterministic: the validator allows several quick reads in one plan, but a guest has exactly one read per session.

### Success marks per tool

```
search_papers     zero results / source quota / empty query → unmarked (stop)
                  provider error / seen-set error / persist error → error (fail)
                  SearchResult delivered → markSearchDelivered
read_paper_*      unknown ordinal / full text unavailable / model not configured → unmarked
                  generic full-text error, stream/complete error, empty content → error
                  stream ok or deliver.Read ok → marked
compare_papers    unresolvable ordinals / full text unavailable → unmarked
                  generic full-text error → deliver.Text + nil → unmarked (recorded "stopped", not "failed")
                  model error → error; success → marked
```

Compare and read handle a generic full-text error differently: compare records `stopped`, read records `failed`. The compare return value predates this change, but step status now exposes it.

### Weak-relevance note ordering

The note ("#3 相关性为低，仍按你的要求继续对比") is sent as its own message before `executeToolCall`, which means before the gate runs. If the gate then refuses, the user sees a promise to continue followed by an error. The note also gives the step a second outgoing message, while the glossary says it belongs in the result.

### Multi-step search segment and data source

`stepInput.Content = searchSegment(input.Content)` replaces the whole step input. `search()` reads `input.Content` for `searchSource` (the ADR 0018 source choice) as well as for the overrides, while ADR §11 restricts the segment to the count/continue/slash overrides. So a source named after the first boundary is lost, and a restart defaults to arXiv:

```
"找联邦学习论文，只要 IEEE 的，然后对比最相关的两篇"
  segment = "找联邦学习论文" → searchSource → arXiv
```

### Guest reservation and per-step gating

Each guest read reserves in `BeforeTool` and releases in the deferred finish unless `deliver.readCommitted` is set. That flag and `guestReservationID` belong to the deliverer for the whole turn and are never reset between steps. Today the stale flag is never consulted, because a second guest read is refused at reserve time (the first read consumed the session). If a later reservation ever succeeded after an earlier committed read and then failed, the finish would skip `FinishGuestDeepRead` and leave the guest stuck in `reserved`, with `ErrGuestTaskInProgress` on every later attempt.

### QQ behaviour

Plan rejections, including the new keyword gate on compare/deep read, now reach QQ as clarifications. That matches decision 5, but QQ users who phrase a comparison differently will see a change in behaviour.

Single-step plans with invalid arguments (ordinal 0, empty rename title, missing search fields) skip validation and fail in `executeToolCall`. `handleQQ` returns the error, and `runUserWorker` logs it and drops the dedupe entry. The user gets no reply, and resending runs the planner again. The old Executor path could not be compared because there is no repository history.

### Trace and admin accounting

`stepErrorCode` labels only `failed` steps, so when delivering a stop note fails, the turn gets an error code but no step carries one. Rejected plans are not traced, because the clarify path drops `plan.Steps`, so the admin view has no record of which plans the validator refused. `toolDistribution` sums `usage.costUsd` per v3 step but the whole turn cost (router + executor + tool) for legacy rows. Over a mixed date range, v3 tools therefore look cheaper per call than their history.

### Test coverage

Covered: transition-table accept/reject cases, QQ one-step limit, literal count from the segment, one-call planning, slash commands bypassing the model, selector resolution against the displayed list with the weak-relevance note, too-few-papers stop, zero-result stop with not-run note, and a full two-step Web turn with step labels and v3 trace.

Not tested: a failing step mid-plan, gate refusal at step 2 (rate limit, guest exhausted), guest plans with two reads, a source mention after the boundary, read/compare stop marks (full text unavailable, unknown ordinal), the `比较`/`不需要` keyword cases, `handleQQ` end-to-end through `planTurn`/`executePlan`, and the `JSON_TABLE` admin query (no MySQL tests).
