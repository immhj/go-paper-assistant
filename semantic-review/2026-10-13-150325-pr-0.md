# Web 对话接入 DeepSeek SSE 增量输出

本次实现让 Web 的精读、论文比较和研究问答直接转发 DeepSeek delta，并用一条预留 bot 消息在结束时保存完整正文；QQ 仍走完整生成后的 replace-stream。结构化 Router、Executor 和检索 JSON 调用继续使用 `Complete`/`CallTool`。成功路径中，前端复用一个 `resultBubble` 追加 prefix、模型 delta 和 suffix，结束后以历史记录替换临时 DOM。阻断问题集中在断线和失败状态，而不是正常 delta 拼接。

**Watch for:** **[高][confirmed]** SSE 断线会取消模型并退还访客资格，违反“断线不退还”；**[高][confirmed]** 流失败会同时留下部分结果、失败说明和错误气泡；**[高][confirmed]** 有效精读保存后若资格提交失败，访客会长期停在 `reserved`；**[中][confirmed]** 中断流通常拿不到尾部 usage，成本熔断会少记模型成本。

**Verdict**: NEEDS_CHANGES

## High-level view

Web 通过可选的 `modelStreamDeliverer` 进入 DeepSeek `Stream`，QQ 因未实现该能力而回退原有 `Complete` 和 QQ 发送逻辑。模型生成的最终自然语言路径均已覆盖；Router `respond/clarify` 和论文检索总结仍整段发送，是要求保持不变的结构化 JSON 路径。

成功流按接收顺序追加 delta，正文超过 10,000 rune 时只追加一次截断标记，suffix 只发送一次；前端在单次请求内复用同一结果气泡。当前代码没有显示成功路径会重复或丢失 delta。

当前任务绑定 HTTP 请求 context。浏览器主动取消、五分钟超时或连接写失败都会终止 DeepSeek 请求，工具 gate 随后把未持久化的访客精读当作系统失败退还资格，允许访客看到部分输出后重新获得免费资格。

失败消息采用 `reserved → content update → sent/failed` 的独立写入，而 Web 历史不按 delivery status 过滤。失败流会把部分结果当作普通 bot 历史展示，再保存失败说明；实时页面还会增加 error 气泡。

资格消费发生在 bot 消息标记 `sent` 之后。`FinishGuestDeepRead(..., true)` 失败时，defer 因 `readPersisted=true` 既不释放也不重试，后续精读和访客导入持续返回 in-progress。

DeepSeek usage 只从流尾 usage 帧取得。断线或 delta emit 失败会在该帧之前返回，使实际产生的部分模型成本不进入成本熔断窗口。

## 客户端断线被当作可退还的系统失败

**[高][confirmed]** `RunWebTurn` 把请求 context 传到 `a.model.Stream`（`internal/service/turn.go:45-59`、`internal/service/web.go:256`），SSE 写失败从 `emitDelta` 返回并终止模型流（`internal/service/web.go:86-107`）。前端还设置固定 300 秒 AbortController（`web/app/index.html:383-384`），长时间深度精读会主动进入同一路径。

只要 `readPersisted` 尚未置位，tool gate 就调用 `FinishGuestDeepRead(..., false)`（`internal/service/web_gate.go:69-80`）。这违反 `docs/specs/0003-free-guest-access-email-verification.md:20,120,156,197` 和 DAO 接口的“client disconnect 不得传 success=false”约束；访客可在看到部分正文后断开并再次获得资格。

修复应在资格预留后切换到服务端拥有且有明确上限的任务 context。SSE 写失败只关闭 emit，模型继续收集并最终落库；有有效结果则消费资格，真正的模型/存储失败且没有有效结果才释放。

## 流失败产生三种机器人输出

**[高][confirmed]** `ModelStream` 失败时保存部分正文并标记 `failed`（`internal/service/web.go:86-107`）；上层再用 `deliver.Text` 保存失败说明（`internal/service/read.go:127-131`、`internal/service/agent_tools.go:116-119,158-161`），`RunWebTurn` 又发送 `status=error`（`internal/service/web.go:279-282`）。前端会为 delta、`message`、`error` 分别建立气泡（`web/app/index.html:393-404`）。

`ListWebConversationMessages` 没有 delivery-status 条件（`internal/dao/mysql/messages.go:222-229`），`renderHistory` 也不检查状态，因此刷新后仍显示 `failed` 部分正文和另一条失败说明；进程中断留下的 prefix-only `reserved` 行也会作为正常答案出现。

流开始后应只维护原消息和原气泡的终态，错误 SSE 只承载机器可读状态。历史默认只展示 user `received` 与 bot `sent`；若要保留部分结果，必须返回 delivery status 并在原气泡显示“未完成”。content 与 delivery status 应由单个 DAO 事务确认。

## 有效精读与访客资格提交存在断点

**[高][confirmed]** 成功流先写完整 content、将消息设为 `sent`，再设置 `readPersisted=true` 并提交资格（`internal/service/web.go:114-131`）。若 `FinishGuestDeepRead(..., true)` 失败，deferred finish 因 `readPersisted=true` 直接返回（`internal/service/web_gate.go:72-80`）；`readCommitted` 没有参与恢复。下一次预留会得到 `ErrGuestTaskInProgress`（`internal/dao/mysql/guests.go:222-266`），正常请求不会重试原 reservation。

修复需要一个原子 DAO 操作同时确认 bot 结果和 consume guest reservation。若暂时不能合并事务，应持久化待提交记录并幂等重试，同时允许资格查询依据已保存结果修复原 reservation；仅交换写入顺序会产生“资格 consumed、结果未保存”的反向不一致。

## 中断流拿不到模型尾部成本

**[中][confirmed]** DeepSeek client 读到 `chunk.Usage` 后才填 token 数，并在 `[DONE]` 后计算完整成本（`internal/provider/deepseek/client.go:228-287`）。`onDelta` 因断线返回错误时会立即返回当时 usage（`internal/provider/deepseek/client.go:263-268`），通常尚未收到流尾 usage。该值进入 `RecordCost`（`internal/service/web.go:276-279,349-356`），所以实际部分消耗被低估。

断线后继续服务端消费流可以取得最终 usage。上游异常仍可能没有尾帧，应按输入与已接收输出计算不低估的 provisional cost，尾帧或账单数据到达后幂等修正。

## Web/QQ 分流缺少主链路回归保护

`modelStreamDeliverer` 仅由 Web 实现（`internal/service/turn.go:32-59`）；QQ deliverer 不实现它，因此精读、比较和研究问答继续落到 `a.model.Complete`（`internal/service/read.go:126-149`、`internal/service/agent_tools.go:115-132,157-175`）。结构化 Router/JSON `Complete` 与 `CallTool` 也保持原路径。

**[中][confirmed]** `internal/service/web_test.go` 只覆盖非流式 `Read` 的访客提交与 emit failure，没有驱动 `ModelStream`、DeepSeek SSE parser、Unicode 截断、handler 断线或前端单气泡归并；`internal/provider/deepseek` 没有 Stream 测试，QQ seam 测试也未断言 Complete fallback 与 replace-stream 序列。`go test ./...` 虽全部通过，仍无法覆盖本次核心行为。

应补充多 delta + Unicode 截断 + suffix 一次、emit 失败后任务继续且资格不退、成功仅一条 sent bot 行、consume 失败可恢复、失败只编码一个终态，以及 QQ 不调用 Stream 且发送序列不变的测试。前端至少需要 fetch-stream/DOM smoke test 验证一次请求复用同一结果气泡。
